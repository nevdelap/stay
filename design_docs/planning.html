Proposed Polish scope

Four daily-use behaviors; the old “Polish” blurb (prompt integration, config naming, README) is handled separately under Scope Decision SD2.

1. Recreate confirm + atomic recreate r / -f

Observed (current): pressing r in the picker kills the session and then sits in the menu; the user must press Enter to actually recreate it. Note: at current HEAD the picker’s r already calls force_recreate_session (kill+create together, no prompt, no second Enter) — so the observed “kill-then-wait” behavior does not match the source and is either a stale build or a runtime failure in the create half. See Q1.

Target: r asks a yes/no confirm first; on Yes it kills and recreates as one action, then returns to the idle list showing the fresh session. On No / Esc: cancel, session untouched. Never a half-done state.

2. Auto-detach when the pane dies

Current (per plan): the relay stays attached after the command exits; the user reviews by staying attached and must detach manually.

Target: when the pane’s command ends (pane goes dead), stay detaches the user back to their shell automatically. The dead pane is left behind (via the existing remain-on-exit) so it can be reattached later to inspect the final screen and its exit code. This is a deliberate change from the written plan (Q3 confirms it is the new intent).

3. Yes/no menu (replaces y/N text prompts)

Current kill confirm:

├────────────────────────────────────────────────────────────────────┤ │ Kill session "build"? y/N │

Proposed: a two-option selector — y/n as keyboard shortcuts, ←/→ to move focus, Enter confirms the focused option. The focused option is the default (safe choice). Shared by kill and recreate.

├────────────────────────────────────────────────────────────────────┤ │ Kill session "build"? Yes No │

Focus is on No (reversed) because that is the safe default for a destructive action. Pressing Enter as-is cancels; the user must consciously move to / type y to confirm. (Exact rendering is the reversed-video focus shown above; carried into the task's acceptance criteria — see Q9.)

4. Refuse to run inside tmux

Target: if $TMUX is set (already inside a tmux session), stay exits with a clear error instead of nesting or fighting the outer tmux for the terminal.

Open questions

Each has options; my pick is tagged recommended.

Recreate

Q1 · is there a real recreate bug or just a stale build?
The observed “kill then wait for Enter” doesn’t match HEAD source. How do we settle it?
recommendedBuild and reproduce the r path now, to know whether we’re fixing a real bug or only adding the missing confirm.
altSpec “confirm + atomic kill+recreate, implementer verifies” and move on.

Reproducing is cheap and removes ambiguity about scope before tasks are written.

Q2 · should recreate re-run the original command, or the default command?
The picker’s r and a bare stay -f name currently recreate with the default command, not whatever the session was running.
recommendedKeep current behavior (default command) for this milestone. CLI users can already re-specify via stay -f name <cmd>.
altMake recreate recall + re-run the original command & cwd (stay would need to store it at create time).

“Recall the original command” is real work and a separate concern; keep Polish focused on the UX confirm/auto-recreate. Revisit if you want it.

Auto-detach

Q3 · how does the relay learn the pane died while attached?
Detection mechanism for pane death during an active attach.
recommendedtmux pane-exited session hook → detach-client. Fires reliably with remain-on-exit on; no polling.
altRelay polls pane_dead on a timer it already runs while attached.
alttmux control-mode (-C) notifications.

The hook is event-driven and reuses the existing detach path the relay already triggers for the detach key.

Q4 · print an “ended (exit N)” line on auto-detach?
Should the user see the exit code at detach time, in addition to it being stay’s own exit code ($?)?
recommendedYes — print e.g. session "build" ended (exit 0) to stderr.
altNo — detach silently; exit code only via $?.

Matches your “go in and look at it and see its exit code” framing; reassuring on auto-detach.

Q5 · always-on, or configurable?
Can the user opt back into the old “stay attached after exit” behavior?
recommendedAlways-on. Reattach-for-review still works; no config surface added.
altAdd a config flag to keep the old stay-attached behavior.

Simpler; the new behavior strictly improves the common case and loses nothing (the pane persists).
